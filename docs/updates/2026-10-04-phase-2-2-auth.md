# Update: Phase 2.2 Auth and Authorization

## Date
2026-10-04

## Summary
Implemented the Fastify auth plugin and a database helper for authenticated, role/permission-checked tenant transactions.

## Why
Phase 2.2 requires Clerk JWT verification while keeping workspace authorization in Formiva's membership database and limiting PostgreSQL tenant context to `withTenant()`.

## Files/areas changed
- `apps/api/src/auth.ts` and API startup: protected `/v1` requests, verified JWT claims using configured remote JWKS, and attached a callback that only runs tenant work inside the DB transaction helper.
- `packages/db/src/with-authorized-tenant.ts` and `withTenant()`: resolved workspace membership from the existing security-definer lookup, mapped the external subject under workspace-only RLS context, and revalidated active membership, role, and permissions under the final transaction.
- `apps/api/test/auth.test.ts`: added synthetic RSA/JWT auth and PostgreSQL membership tests.
- API and database READMEs, changelog, and engineering memory.
- No applied migration was edited and no new migration was needed.

## Security considerations
- JWT verification requires a valid signature, exact issuer, configured audience, unexpired `exp`, `sub`, and an `azp` value in the configured allowlist.
- The workspace header is only compared with database-returned active memberships. Unknown and foreign workspaces use the same `404`.
- Database auth tests ran membership resolution as the `formiva_app` role and used only synthetic fixture users and generated local RSA keys/JWTs; the test JWKS fetch was stubbed and no real Clerk credentials were used.
- PostgreSQL tests connected only to the ephemeral local `formiva_test` database on loopback. No OCI or production connection was made.

## Remaining risks
- Resource endpoints are not part of Phase 2.2; their handlers must perform tenant database work through `request.withTenant()` and use `404` for rows hidden by RLS.
- Production Clerk issuer, audience, JWKS URL, authorized-party allowlist, and database connection must be configured before authenticated routes can be used.

## Migration/deployment notes
- No database migration change is required. The plugin uses the existing `ops.workspaces_for_user` function and current RLS policies.
- Configure `CLERK_ISSUER`, `CLERK_AUDIENCE`, `CLERK_JWKS_URL`, `CLERK_AUTHORIZED_PARTIES`, and `DATABASE_URL` in the API runtime; do not add their values to source control.
