# Formiva CaseFlow — Phase 0 Kit

**Purpose:** run Phase 0 discovery and the Day-1 infrastructure check before application code is written.

**Launch wedge:** employee onboarding and document collection for Indian IT and professional-services firms with 10–100 employees.

**Status:** working kit derived from the current Review & Change Register, Business Plan v2.1, Coding Plan v2.1, and Project Management Dashboard v2.1.

> **Source note — Sales Strategy Stage 1:** The uploaded package did not contain a separate Sales Strategy document, and the Business Plan’s exact Stage 1 question table was not present as extractable content. The interview script below therefore uses the approved Diagnose-stage evidence and dashboard fields: named owner, recurring hiring, process map, baseline measures, tools, rework, time, handoffs, and willingness to pay. It is an internal working synthesis, not a verbatim reproduction of a missing source.

## Part 1 — 40-target-firm criteria and blank tracker

### 1.1 Target-firm selection criteria

Use these criteria to build the initial list of **40 firms**. Mark each firm **Qualified**, **Maybe**, or **Exclude** before outreach.

A strong target should satisfy most of the following:

- [ ] Indian IT or professional-services firm.
- [ ] Approximately **10–100 employees**.
- [ ] Recurring hiring or regular new-joiner onboarding.
- [ ] A named HR, operations, founder, or MSP owner for onboarding.
- [ ] Onboarding is spread across email, spreadsheets, shared folders, and/or manual reminders.
- [ ] Document collection or completeness checking creates visible work.
- [ ] There is recurring rework, chasing, correction, approval delay, or handoff friction.
- [ ] The person interviewed can describe a recent onboarding case with specific numbers or examples.
- [ ] There is a plausible willingness to run a time-boxed diagnostic or pilot.

Usually exclude unless there is a clearly documented exception-management or integration gap:

- [ ] Firms with a well-integrated HRIS/onboarding stack and no painful exception path.
- [ ] Firms outside the launch ICP with no design-partner reason to include them.
- [ ] Prospects asking for a broad universal platform, unrelated vertical pack, or WhatsApp commerce as the first use case.
- [ ] Any prospect requiring real sensitive documents during discovery. Discovery uses conversation and synthetic/redacted examples only.

### 1.2 Evidence rules

Record facts, not impressions.

- Write the customer’s own words for the recurring problem where possible.
- Record concrete counts, durations, volumes, and recent examples.
- Separate **observed evidence** from **your interpretation**.
- Do not count a firm as a discovery success merely because it likes the idea.
- Do not ask for customer documents, ID numbers, production exports, credentials, or secrets.
- A pilot commitment means a written or clearly recorded commitment to a time-boxed employee-onboarding pilot; the register/dashboard refer to a letter of intent or paid-pilot commitment.

### 1.3 Discovery gate

Phase 0 passes only when all of the following are recorded:

- [ ] At least **15 interviews** completed; target range is **15–20**.
- [ ] At least **8 of the first 15** identify the same onboarding rework problem.
- [ ] **3 firms** commit to pilot/design-partner participation.
- [ ] The recurring problem, current process, baseline measures, and pilot interest are documented for each counted firm.
- [ ] If the gate fails, do **not** start Phase 2; change the ICP, offer, or price first.

## Part 2 — 20-minute diagnostic interview script

### Interviewer rules

- This is a **diagnostic**, not a product demo.
- Ask for the most recent real process, not an ideal process.
- Ask “how many?” and “how long?” before accepting “often” or “a lot.”
- Do not lead with Formiva’s proposed solution.
- Do not ask the prospect to send documents, IDs, credentials, exports, or secrets.
- If the customer volunteers sensitive details, stop the detail and record only a safe summary.
- Capture exact wording in quotation marks when it describes the pain.

### 0:00–2:00 — Opening and permission

**Say:**

> Thank you for taking 20 minutes. I’m studying how smaller Indian IT and professional-services firms handle employee onboarding and document collection. I’m not going to pitch a product first. I want to understand your current process, where it breaks, and what the cost is. I’ll take notes, but I do not need any documents or personal data. Is it okay if I ask about your most recent onboarding process?

Ask:

1. What is your role in hiring or onboarding?
2. Are you the person who owns the process, or who else should be involved?
3. May I follow one recent onboarding case from start to finish?

**Record:** named owner, role, recurring hiring, and permission to continue.

### 2:00–5:00 — Map the current process

**Say:**

> Please walk me through the most recent new-hire onboarding case, starting when the person accepts the offer and ending when they are ready for day one.

Ask in sequence:

1. What starts the process?
2. Who sends the first request to the new hire?
3. Where do they enter information?
4. Which documents do you normally request?
5. Where do they upload or send those documents?
6. Who checks whether the information and documents are complete?
7. Who corrects or approves exceptions?
8. What must happen before payroll, IT access, or the hiring manager can proceed?
9. Which steps are manual, repeated, or dependent on one person remembering to follow up?

**Follow-ups:**

- “What happened in the last case?”
- “Who did that step?”
- “What tool or file did they use?”
- “How did the next person know it was ready?”

**Record:** process map, roles, tools, handoffs, and the first obvious delay.

### 5:00–8:00 — Documents and completeness

**Say:**

> Let’s focus only on the information and documents, without sharing any actual document or ID number.

Ask:

1. Which requested fields or documents are most often missing?
2. Which documents are hardest for the new hire to submit correctly?
3. What makes a submission “complete” in your current process?
4. What mistakes do reviewers catch repeatedly?
5. How do you tell the new hire exactly what needs correction?
6. How many rounds of clarification are typical?
7. Are different people checking different parts of the submission?
8. Are there language, format, mobile-upload, or scan-quality issues?

**Follow-ups:**

- “Can you give me a recent example without sharing the document itself?”
- “What did the reviewer have to do next?”
- “How long did the correction take?”

**Record:** document classes, completeness definition, repeated errors, and correction loops.

### 8:00–11:00 — Rework and failure points

**Say:**

> Where does the process most often go backwards or require someone to redo work?

Ask:

1. What is the most common rework problem?
2. How frequently does it happen: per hire, per week, or per month?
3. What triggers it?
4. Who notices it?
5. Who contacts the new hire or another team member?
6. How many reminders are normally needed?
7. What happens when the problem is not resolved on time?
8. Does the issue delay joining, payroll, access, compliance review, or another downstream step?
9. Which exceptions are safe to resolve quickly, and which require human judgment?
10. What is the most expensive or embarrassing failure mode?

**Required capture:** one verbatim pain statement and one recent concrete example.

### 11:00–13:00 — Time, volume, and baseline

**Say:**

> I want to put a rough baseline around this. Estimates are fine if we label them as estimates.

Ask:

1. How many new hires do you onboard in a typical month?
2. How long from offer acceptance to “ready for day one”?
3. How many HR or operations minutes are spent per hire?
4. How much time is spent chasing missing information or documents?
5. How many people touch the process?
6. What percentage is complete correctly on the first submission, approximately?
7. How many cases miss the intended approval or onboarding SLA?
8. What is the effect of a delayed or incomplete case?
9. What would you measure if you wanted to prove improvement?

**Record:** time-to-ready, volume, labor minutes, first-pass completeness, reminder/rework count, and SLA impact.

### 13:00–15:00 — Tools and handoffs

**Ask:**

1. Which tools are used today: email, spreadsheets, shared folders, HRIS, messaging, ticketing, or something else?
2. Where is the current source of truth?
3. Which handoff is most error-prone?
4. Where do duplicate entries or conflicting versions appear?
5. Which downstream system must receive the final approved record?
6. What happens when an external write or notification fails?
7. Which current tool do people like, and which tool do they work around?
8. Have you tried to fix this before? What happened?

**Record:** current stack, integration target, workarounds, and prior attempts.

### 15:00–17:00 — Impact and priority

**Ask:**

1. If this problem stayed unchanged for the next six months, what would it cost you?
2. Who feels the pain most strongly?
3. Who would approve a change to the process?
4. Is this a “must fix,” “should fix,” or “nice to have” problem?
5. What other initiatives compete for attention?
6. What would make this problem urgent enough to act on now?
7. What evidence would you need before trusting a new process with onboarding work?

**Record:** urgency, buyer, internal approval path, and trust requirements.

### 17:00–19:00 — Pilot qualification, without overpromising

**Say:**

> Based on what you described, I’m considering a small, time-boxed diagnostic or pilot focused only on employee onboarding and document collection. It would start with synthetic or redacted data unless a separate sensitive-data gate is passed. I’m not asking you to decide now, but I’d like to understand what a useful test would look like.

Ask:

1. Would you consider a time-boxed pilot of this one workflow?
2. What process boundary should the pilot include and exclude?
3. What baseline should we record before starting?
4. What outcome would count as useful?
5. Who would need to participate?
6. What data could be used safely for an initial test?
7. What would prevent you from participating?
8. If the test showed measurable improvement, would this become a paid implementation or paid pilot discussion?
9. What would you expect to pay for implementation or ongoing use, if anything? Treat the answer as a pricing hypothesis, not a commitment.

**Record:** pilot scope, data boundary, success measure, participants, blocker, and commitment level.

### 19:00–20:00 — Close and referral

**Say:**

> Let me check that I heard you correctly: the current process is [one-sentence summary], the main rework problem is [customer’s words], it happens [frequency], and it costs roughly [time/impact]. Is that accurate?

Then ask:

1. What did I misunderstand?
2. Who else should I speak with?
3. May I follow up with a one-page summary of the baseline and a proposed diagnostic scope?
4. What is the best date for that follow-up?

**Close without claiming validation:**

> Thank you. I’ll separate what you told me from my own interpretation and will not treat this interview as proof until the same pattern appears across multiple firms.

### Interview completion check

- [ ] Named owner recorded.
- [ ] Recurring hiring confirmed or rejected.
- [ ] Current process mapped.
- [ ] Current tools and handoffs recorded.
- [ ] One costly document or rework problem captured in the customer’s words.
- [ ] Frequency recorded.
- [ ] Time/labor baseline recorded.
- [ ] Recent concrete example recorded.
- [ ] Pilot interest and commitment level recorded.
- [ ] No customer document, real ID number, secret, or credential collected.

## Part 3 — Day-1 OCI console checklist

### Scope and governing rules

This checklist is for the **OCI console check required by the Review & Change Register**. It is not permission to resize, upgrade, purchase, or deploy.

Current governing baseline:

- No paid infrastructure without a new explicit decision.
- Two separate OCI accounts are the current intended architecture.
- VM1: API, workers, PostgreSQL, and ClamAV.
- VM2: AI Engine only.
- Intended shape in the current ADR-01: **2 OCPU / 12 GB / 200 GB per VM**, subject to the console check.
- Do not claim that two Always Free accounts under one person are permitted; check the applicable Oracle terms and account ownership situation.
- Do not put customer documents, real ID numbers, credentials, or secrets into screenshots or notes.

### B. Check Server #1 status

1. [ ] Open the correct OCI Console tenancy.
2. [ ] Open **Compute → Instances**.
3. [ ] Locate the instance named `instance-20260530-1135`.
4. [ ] Record whether it is **Running**, **Stopped**, **Terminated**, or another state.
5. [ ] Record the availability domain and region.
6. [ ] Record the shape name.
7. [ ] Record the OCPU count and memory shown by OCI.
8. [ ] Record the boot-volume size and any attached block volumes.
9. [ ] Check whether the instance is marked Always Free eligible or otherwise associated with a paid account.
10. [ ] Record any warning, reclaim, capacity, suspension, or billing notice.

**Stop and escalate if:**

- The instance is not the expected Server #1.
- The console shows a paid shape or unexpected billing.
- OCI shows a reclaim, suspension, or account-verification warning.
- The actual shape differs from the approved baseline and the difference would change the architecture.

### C. Check the tenancy’s compute allowance

1. [ ] Open the tenancy’s **Limits, Quotas and Usage** view, or the equivalent current OCI quota page.
2. [ ] Select the relevant region.
3. [ ] Find the Ampere A1 compute limit.
4. [ ] Record the total OCPU limit shown.
5. [ ] Record the total memory limit shown.
6. [ ] Record current usage and remaining capacity.
7. [ ] Repeat for the second OCI account if it exists and is authorized for this project.
8. [ ] Record whether the console shows the reported **2 OCPU / 12 GB** ceiling or an older **4 OCPU / 24 GB** ceiling.

Do not infer capacity from a blog post or from the desired architecture. Use the console result as the evidence for the next decision.

### D. Check block-storage allowance

1. [ ] Open the tenancy’s storage limits/quotas for the region.
2. [ ] Record total Always Free block-storage capacity shown.
3. [ ] Record current allocated and used storage.
4. [ ] Repeat for the second account.
5. [ ] Compare the result with the intended 200 GB per VM baseline.
6. [ ] Do not resize Server #1 or create the final VM2 disk shape today.
7. [ ] Record any storage limit, reclaim, or billing warning.

If the console shows only 200 GB total for one account, record that as a constraint and leave the size decision open. Do not silently use the old 150 GB + 50 GB fallback or silently choose another provider.

### E. Check account and terms status

1. [ ] Open **Governance / Tenancy details / Account management** or the current equivalent.
2. [ ] Record whether the account is Always Free, Pay-As-You-Go, or another account type.
3. [ ] Check Oracle messages and email notices since June 2026.
4. [ ] Look for notices about idle resource reclamation, shape limits, quota changes, verification, or account suspension.
5. [ ] Do not upgrade to Pay-As-You-Go as part of this checklist.
6. [ ] If the second account is held under another person or entity, record that the ownership/terms question requires the account holder’s authorization and direct terms review.

### F. Security check before touching the server

This is a console-side precondition check; it does not replace the Phase 1 hardening task.

- [ ] Confirm whether Server #1 currently has a public IPv4 address.
- [ ] Record whether SSH/port 22 is exposed in the OCI security list or NSG.
- [ ] Do not open port 22 broadly to the internet.
- [ ] Do not upload customer data.
- [ ] Do not create a database, AI model, bucket, credential, or production service today merely because the instance is running.
- [ ] Plan the hardening action: key-only SSH, password login disabled, root login disabled, `NOPASSWD:ALL` replaced, least-privilege access, and no public port 22.
- [ ] Keep a second tested administrative access path before disabling the current login method.
